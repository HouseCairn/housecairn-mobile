## Alignment with the web application

The app carries rules of the web application: the recurrence and seasons
(`housecairn.tasks.recurrence`), the library of task templates (`tasks/task_templates.yaml`,
web ADR 0049) and the design tokens (`design/tokens.json`). A change of the web reaches the app
without depending on anyone's memory:

- **One pin.** `tool/web_alignment.json` names the release and commit of HouseCairn/housecairn
  each element was aligned on. It moves only through `python3 tool/web_alignment.py update
  --web <clone> --release vX.Y.Z`, which regenerates what follows mechanically: the recurrence
  vectors (`tool/recurrence_vectors.py`, run in the web environment of the pinned commit,
  `uv sync --frozen --no-dev`), the templates (`assets/task_templates.yaml`, a copy) and the web
  values of the design tokens (the app may add its own tokens, never change a web one).
- **A check on every pull request.** The `Web alignment` job of CI regenerates every element at
  its pin and compares: the vectors and templates byte for byte, the tokens value by value. A
  vector edited by hand, a token that is not the web's or a missing pin fails it. The tool has
  its own tests (`tool/test_web_alignment.py`, run by the same job): a release without effect, a
  real gap, a missing or modified token, a missing pin, a file outside the list. A fourth
  element, `web_parity`, is the measure of the web's rendering that `test/web_parity_test.dart`
  compares the app with: taken in a browser (`tool/web_parity.py`), never regenerated by
  `update`, it names the release it was taken at, and `check` fails when that is not its pin;
  the pin moves only with a release that changes a file drawing the measured screens.
- **A pull request when the web moves, and only then.** The daily `Web alignment` workflow
  compares with the latest web release. It opens, or updates, a pull request only when a file the
  app carries would differ: a recurrence vector, a task template or a design token (the source
  header of the vectors, which names the commit, does not count). A release that changes none of
  them is "checked, nothing to port": the run says so in its summary, writes nothing and opens
  nothing, and the pin stays on the last release that mattered (`check` compares each element
  with its own pinned commit, so the app stays consistent; the pin moves with the next release
  that changes a ported file). When something differs, the workflow runs `flutter test` on the
  regenerated files and opens, or updates, the one pull request of the branch
  `web-alignment/housecairn`, with the new pin and a report of the web files that changed, those
  cited by the [spec](spec.md) included. When the tests fail, a rule changed on the web: the pull
  request says that Dart code is needed, and stays red until it is ported on that branch. It is
  opened with the project's GitHub App (environment `app-update`), as the app update of the Home
  Assistant add-on. The job that runs the web code makes a patch; the patch may hold only the four
  files the update writes (the three ported files and `tool/web_alignment.json`), checked by
  `tool/web_alignment.py verify-patch` in that job and again in the job that holds the App's
  token. Another path fails the run and lists the paths.
  Its bot login, `<slug>[bot]`, is exempt from the `CLA` check (`APP_BOT` in
  `.github/scripts/cla.js`, a placeholder until the App exists).
- What no script ports, the data model and the rules of the spec, is read by a person: the
  report lists the web files cited by the spec that changed since the commit the spec names.

## Lot 4. Sync engine (without network, without crypto)

**Scope**: operations, HLC, apply and merge rules, deterministic ids, repair rules, schema
versions (`sv`, `extra`, `pending`, `min_sv`), snapshots, behind the `SyncTransport` of lot 2c,
against in-memory doubles of it.

**Acceptance**:
- Property tests: random histories of 2 to 5 devices **over at least two homes**, applied in
  random orders and with duplicates, give identical databases (compared row by row and field by
  field).
- Homes: the same deterministic name (`envelope:2027`) in two homes gives two rows; a reference
  to a row of another home is read as empty; `archived_at` merges as last writer wins; a
  **purge** of one home (a log record, given by the relay double), mixed in random order with
  offline edits of that home carrying later clocks, always ends with no row of it and the other
  home unchanged.
- The cases of [ADR 0003](adr/0003-sync-protocol.md) each have a named test: two closings of
  one occurrence, postpone against done, undo against an edit of the successor, the same article
  drawn twice, deletion against edit, restore, a device on an older `sv` that keeps unknown
  fields.
- A new device that starts from a snapshot and the batches after it equals one that replayed
  everything.
- HLC: a device whose clock is a day ahead does not move the others' clocks.
- The engine knows no transport: the same property tests pass with a double of the relay
  (batches and positions) and a double of a server (a cursor, and an answer that gives the value
  that won for each field), as [ADR 0010](adr/0010-three-ways-to-use-the-app.md) describes.

**Device**: none.

**Depends on**: lot 3 (every entity exists) and lot 2c (the transport interface).

is on the server in this way: no relay next to it, no home kept only on the phone.

**Acceptance**:
- Against a Housecairn instance started in CI from its image, at the web release that brings the
  sync API: a change made on the phone is read through the web API, and a change made through
  the web API reaches the phone.
- The cases of [ADR 0003](adr/0003-sync-protocol.md) each have a named test with one side on the
  phone offline and the other on the web: the phone and the server end equal, field by field.
- Deletions made on the web reach the phone, those that the web makes without `updated_at` or
  without a row left included (the list of ADR 0010); an erased home is erased from the phone as
  a purge.
- Send with **two homes**: every id on the server is the phone's; a send cut in the middle and
  repeated creates no duplicate. Take: the local homes are removed only after the export was
  offered and the confirmation typed; cancelling leaves the phone as it was.
- Disconnect removes the credential of the access from `Store`; unsent changes are listed first.
- After a 410 the phone reconciles by the rule of
  [protocol section 2.10](protocol.md#210-with-a-housecairn-server), each case a named test: a
  row created offline and never seen by the server is sent again, a row deleted by someone else
  during the absence and purged is deleted on the phone, a waiting change to a purged row is
  dropped and listed, a waiting change to a row still there is decided field by field.
- No request goes to another host than the address typed; `http://` is refused unless the host
  is a local IP literal (protocol section 2.10; a name, `.local` included, is refused), and
  then a warning is shown first; a
  certificate error is shown and cannot be skipped; the credential is never in a log, the
  database or an export (tests).
- The sign-in uses the system browser with PKCE, and no token is typed or pasted; revoking the
  access on the server stops the phone at its next call, and the phone says so.
- The way stays locked until the purchase is made (or restored); the first way and the data
  of the phone are untouched by a refused or cancelled purchase.
- Reminders on the phone cover the tasks of the signed-in account and the tasks with no
  assignee.
- A server too old for the sync API is refused with a message that names the version needed.

**Device**: a phone against the Home Assistant add-on and against the web application on a home
server; a day in airplane mode with edits on both sides, then sync.

**Depends on**: lot 4; and a lot of the web repository, `HouseCairn/housecairn`, that brings the

## Lot 5. Encryption and family

**Scope**: device keys in secure storage; epochs; batch, snapshot and blob formats of
[protocol.md](protocol.md); membership log; invitation by QR code with the six-digit code;
removal and rotation; recovery code; members and assignment; encrypted export and import.

**Acceptance**:
- Test vectors for every byte format (batch, snapshot, blob, record, envelope, invitation,
  backup) are committed and checked by the Dart code; the relay (lot 6) checks the same file.
- Tampering tests: a changed byte of a header, a ciphertext or a signature is rejected; a record
  signed by a non-admin is rejected, a `purge` of a home included; a batch of a removed device
  above `last_seq` is rejected.
- Blob format: a blob checked against the wrong blob id or space (swapped blobs), cut before its
  `FINAL` chunk, or of another size than its reference, is rejected.
- With **two homes**: an invited phone receives both homes and their photos; after a removal, the
  removed device's keys open no batch of the new epoch, for either home.
- Recovery: from the code alone, a new install gets every row and photo of both homes back
  (in-memory relay).
- Export with two homes, then import into a fresh install, gives the same rows and files; import
  as a copy of one home of the file adds that home with new ids next to the existing ones; a
  wrong passphrase gives a clear error and no partial data.
- Export compliance revisited: `ITSAppUsesNonExemptEncryption` and the store declarations match
  the cryptography of this lot ([ADR 0009](adr/0009-early-testflight-builds.md)).

**Device**: QR invitation between an Android phone and an iPhone; keys survive an app update and
are gone after uninstall; the export file is shared to and imported from the Files app.

**Depends on**: lot 4. Before it starts: a review of the protocol by someone with cryptography
experience is requested (it may run in parallel with lot 5, it must end before lot 8).

**Device**: purchase, renewal, cancellation and restore in the App Store sandbox and with a
Google Play licence tester; refund seen by the relay.

**Depends on**: lot 6; products created by the maintainer in App Store Connect and Google
Play Console; price and trial decided ([open questions](#open-questions)).

## After v1

Decided by the maintainer as later work, not to be made impossible: reading a web archive
(format 3) in the app; an Android build without Google services (UnifiedPush, F-Droid), after
1.0; a home shared with someone outside the family (a second space on one phone).

Decided as later work by the maintainer on 2026-11-14 ([ADR 0010](adr/0010-three-ways-to-use-the-app.md)):
merging the homes of a phone with those of a server when both have data (in v1 the person keeps
one side); a direct move between family sync and a server, without going through Alone.
A phone in two ways at once is not planned at all: one way at a time.

A Housecairn instance acting as the relay, listed here before, is replaced by lot 4b, which
means something else: the server reads the data, where the relay never can.

## Open questions

Choices of the maintainer, still open. Nothing in these documents sets a price. The questions
raised by [ADR 0010](adr/0010-three-ways-to-use-the-app.md) (numbered 4 to 14) were answered on
2026-11-14 and are written in that record, in the lots above and in the section After v1.

1. **Price** of the hosted family sync, monthly and yearly.
2. **Free trial**: whether there is one, and how long.
3. **End of a subscription**: proposed in [ADR 0006](adr/0006-subscription.md), 30 days during
   which the space is read only, then deletion, with notices at 7 days and 1 day; to confirm
   or change.
4. **A licence exception for `dbus`** (lot 2b), **accepted on 2026-11-15**: the Linux part of `flutter_local_notifications`
   pulls `dbus` (MPL-2.0, a file-level weak copyleft) into `pubspec.lock`; no iOS or Android
   build contains it and the app changes none of its files. The check reads the GNU licences
   that the MPL text names as secondary licences as if they applied, so the package has one
   named exception in `tool/licenses/exceptions.txt`, with its reason. Its scope stays that
   package; replacing the notification package would end it.
